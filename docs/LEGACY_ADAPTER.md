# 架构选择与后续升级路径

## 本地数据层

**当前参考版**：`portfolio.sqlite3` 是权威数据源，PDP `pdp.py` 是唯一增量写入入口。

- `assets`：资产定义与所在账户。
- `transactions`：真实交易和现金流的来源行。
- `snapshots`：各日期拍摄的市值/收益展示；交易与快照不能相互替代。
- `pdp_*`：更新协议独立表，保存主数据库 ID、数据指纹、包应用历史、每项变更原值/新值、业务唯一键、作废标记、十进制金额原文。

## 为什么本阶段不采用 SQLite 二进制 Changeset

SQLite Session Extension 提供很强的变更集能力，不过其用途通常是两个同构数据库中的二进制变更同步，而且环境中需要支持该扩展。本场景原始来源是人工截图和券商导出，AI 本来就需要**基于金融业务语义构造交易**，若直接给出二进制数据库 diff，用户难以预览，也不利于标注“源截图/未确认价格/申购和确认日期”。

因此先选择可读可审计的 JSON 更新包、SQLite 事务和备份，成本更小、可跨 Windows/macOS/Linux 运行。日后真正出现多设备协同编辑需求，再评估 SQLite session、CRDT 或服务端日志复制。

## 不应忽略的长期数据质量问题

1. **外币原币流水**：现有数据库金额有 `*_cny` 字段，暂不建议继续添加美元/港元交易金额。下一版使用 `original_currency` + `amount_minor` (或 `amount_decimal_text`) + `fx_rate` + `fx_date`，换算形成派生数据而不是覆盖原币。
2. **现金流归属**：资产内部买卖与账户入/出金是不同层级的现金流，不可混算为组合外部资金流。
3. **成本基准**：需要收集交易费、转托管、税项、分红、债券买入应计利息与后续票息，才能计算可信的真实收益率。
4. **价格采集与净值**：截图采集日只是观察时间；申购下单日、确认日、净值所属日与当前市场价格日要分别保存。
5. **数据可信等级**：未来添加 `claims`/`evidence` 层让每个字段能映射到原始凭证及识别质量分数；v1 暂以每条操作的来源注释和证据哈希为粒度。

## 推荐 v2 升级

保持 PDP 对话交互格式不变，迁移底层业务数据到 `accounts`（账户）、`instruments`（金融产品）、`lots`（成本批次）、`cashflows`（现金流）、`trades`（成交）、`valuations`（估值）、`fx_rates`（汇率）、`evidence`（凭证）、`audit_events`（审计）等结构化实体，以整数最小货币单位或十进制字符串保存精确货币。

这应当是**单独审核的数据库迁移**而非混入日常增量补丁。迁移后需要建立可逆映射与全面行数、合计校验。
